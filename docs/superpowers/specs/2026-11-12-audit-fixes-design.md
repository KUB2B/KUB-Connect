# Аудит KUB Connect v1.4.0 и спека исправлений

Дата: 2026-11-12. База: `main` @ `3a933f9`.

## 1. Что проверено

- Прочитан весь не-тестовый Go-код (`main`, `internal/*`, `cmd/headless`), `frontend/src/main.ts`,
  Makefile, `scripts/build-windows.sh`, `release.yml` (GitHub и GitVerse), NSIS-скрипт.
- `go vet ./...` (linux) и `GOOS=windows go vet ./...` — чисто.
- `go test ./...` — все пакеты проходят; `go test -race` для `app`, `logbus`, `tunnel`, `store` — чисто.
- Поведение xray-core сверено по исходникам в module cache (`v1.260327.0`): лог-файл открывается
  с `O_APPEND`, `sockopt.interface` на Windows поддержан, `Host` в `headers` для ws — deprecated.

Не проверено:

- **`govulncheck`** — запуск заблокирован политикой сессии. Зависимости от марта–мая 2026
  (xray-core `v1.260327.0`, tun2socks от 2026-05-07), проверить вручную:
  `go run golang.org/x/vuln/cmd/govulncheck@latest ./...`
- Ничего не запускалось на Windows и на хосте с IPv6. Пункты, где вывод сделан только по коду
  и требует подтверждения на живой системе, помечены **[проверить]**.

Общая оценка: слои разделены чисто, откаты при частичном старте продуманы, тестов много, XSS во
фронтенде нет (везде `textContent`). Проблемы сосредоточены в трёх местах: границы привилегий
(elevated-процесс доверяет файлам из пользовательского каталога), отсутствие реакции на события
после подключения (смена сети, падение) и утечки мимо туннеля (IPv6, DNS).

## 2. Проблемы

Серьёзность: **В** — высокая, **С** — средняя, **Н** — низкая.

### 2.1 Безопасность

| ID | Сер. | Где | Проблема |
|----|------|-----|----------|
| S1 | В | `internal/wintundll/extract.go:36`, `load_windows.go` | `wintun.dll` распаковывается в `%LocalAppData%\kub-connect` (каталог доступен на запись обычному пользователю) и загружается в **elevated**-процесс. ## 3. Спека исправлений

Принцип: минимальный дифф, без новых абстракций. Каждый пункт — отдельный коммит с тестом.

### Фаза 1 — безопасность и «сломанный интернет» (сначала)

**S1. Wintun DLL.**
1. `wintundll.extract`: сравнивать содержимое, а не размер — `os.ReadFile(dst)` + `bytes.Equal`
   (файл ~430 КБ, читается один раз за процесс). При расхождении перезаписать.
2. NSIS: класть `wintun.dll` в `$INSTDIR` (каталог в Program Files, запись только администратору).
   `Ensure()` сначала пробует `<каталог exe>\wintun.dll` по абсолютному пути и только при
   отсутствии файла распаковывает в кэш (dev-сборки, портативный запуск).
3. Тест: `extract` перезаписывает файл того же размера с другим содержимым.

Шаг 1 сужает окно атаки до гонки между проверкой и `LoadLibraryEx`; шаг 2 закрывает его для
установленной версии.

**S2. Обновление.**
1. `Asset` получает поле `Digest string` (`json:"digest"`, GitHub отдаёт `sha256:<hex>`).
   `Download` считает SHA-256 через `io.MultiWriter` и сверяет; пустой или несовпавший digest —
   ошибка, файл удаляется.
2. Скачивать в каталог из `os.MkdirTemp`, а не под предсказуемым именем.
3. `http.Client{Timeout: 15 * time.Minute}` для скачивания; `CheckLatest` возвращает ошибку
   при статусе ≠ 200.
4. Тесты: несовпадение digest → ошибка и нет файла; 403 от API → ошибка.

Не входит: подпись Authenticode и `WinVerifyTrust` — нужен сертификат; вернуться, когда появится.
Digest защищает от подмены на диске и битой загрузки, но не от компрометации GitHub-аккаунта.

**B1. Остатки kill switch.** В `App.startup` рядом с `sysproxy.ClearStale()`:
если `privilege.IsElevated()` — `firewall.New().Off()` (идемпотентно, на не-Linux no-op).
Без root удалить таблицу нельзя — записать предупреждение в лог. Документировать в `tun-mode.md`.

**B3. IPv6 в TUN + whitelist.**
1. `connect.go`: в ветке `bindIface != ""` — `cc.BlockIPv6 = true` всегда (не только при `Full`).
2. `xrayconf.Options.BlockIPv6`: при `true` добавлять правило `block ::/0` сразу после loop-guard
   (тем же приёмом, что `withLoopGuard`). `fullRules` своё правило сохраняет.
3. Тест в `build_test.go` на наличие правила; тест в `connect_test.go` на `BlockIPv6` в whitelist.
4. Проверить на хосте с IPv6: сайты открываются через откат на IPv4, пресеты идут через VPN.

Цена: в TUN-режиме IPv6 недоступен целиком. Это уже так в full-tunnel; полноценная маршрутизация
IPv6 через туннель — отдельная задача, если понадобится.

**B6. Окно на Linux.** `HideToTray`: при `runtime.GOOS == "linux"` — `WindowMinimise` вместо
`WindowHide`. Одна строка.

### Фаза 2 — надёжность соединения

**B2. Лог xray.** В `Service.Connect` перед `Factory`: `os.Truncate(s.xrayLogPath(), 0)`
(ошибку «нет файла» игнорировать). Тест: два подключения подряд — строки первой сессии не
появляются в шине повторно.

**B5. DNS под мьютексом.** `resolveServerIPv4`:
`net.DefaultResolver.LookupIP(ctx, "ip4", host)` с `context.WithTimeout(3 * time.Second)`.
Разделение `s.mu` на «состояние» и «операцию» не делаем: события `state` уже уходят во фронтенд
из-под замка, так что UI не замирает; вернуться, если понадобится отмена подключения.

**B4. Смена сети.** Наблюдатель в `internal/app`, только для TUN-режима:
1. При успешном Connect запомнить `(gateway, interface)` и запустить горутину с тикером 5 с,
   которая вызывает `deps.DefaultInterface` (расширить до возврата шлюза).
2. Если пара изменилась или маршрут по умолчанию пропал и появился снова — запись в лог
   «сеть изменилась — переподключение» и `Disconnect()` + `Connect()`.
3. Пока маршрута нет — ждать, ничего не трогать. Останавливать горутину в `Disconnect`.
4. Тест с подменой `DefaultInterface`: смена значения вызывает ровно одно переподключение.

`// ponytail:` опрос раз в 5 с вместо `NotifyRouteChange2`/netlink — заменить, если задержка
переподключения окажется заметной. Проверку «жив ли туннель» (HTTP-проба через SOCKS) не
добавляем, пока нет жалоб на зависшие сессии при неизменной сети.

**B7. Смена сервера при активном соединении.** `SetActiveServer` при `ConnConnected` после
сохранения делает `Disconnect()` + `Connect()`. `RemoveServer` активного сервера при активном
соединении — ошибка «сначала отключитесь». Тесты на оба случая.

**B8. Битое состояние.** `store.Load` возвращает третьим значением путь бэкапа (пусто, если всё
в порядке); `app.New` пишет в шину и в `lastError` «Настройки повреждены и сброшены, копия: …».
В `Load` отфильтровывать `nil` из `Servers`.

**A2. DNS в full-tunnel.** **[сначала подтвердить утечку на Windows: `nslookup` + Wireshark]**
1. `netcfg.Config.DNS []string`; заполняется (`1.1.1.1`, `8.8.8.8`) только при `Profile.Full` в TUN.
2. Windows: `netsh interface ipv4 set dnsservers name=<tun> static <ip> validate=no` + низкая
   метрика интерфейса TUN, чтобы резолвер выбирал его. Адрес исчезает вместе с адаптером.
3. Linux: `resolvectl dns <tun> <ip>` + `resolvectl domain <tun> "~."`; при отсутствии
   `resolvectl` — предупреждение в лог, без ошибки.
4. Тесты генераторов команд по образцу `route_cmds_test.go`.

В whitelist-режиме DNS остаётся локальным — это соответствует модели «всё напрямую, кроме списка».

`state`, построчные события лога — на реальных объёмах это незаметно (после B2 тем более).

Гипотеза для замера: xray-DNS `["1.1.1.1", "localhost"]` (`build.go:164`) в whitelist-режиме
идёт на 1.1.1.1 напрямую; если адрес у провайдера недоступен, первые соединения SOCKS5-клиентов
с доменными именами ждут таймаута до отката на `localhost`. Если подтвердится — в whitelist
поменять порядок.
